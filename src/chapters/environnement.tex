\section{Environnement de déploiement et de test (C2.1.1)}
\competence{C2.1.1}{Protocole de déploiement continu, critères de qualité et de performance}{Non}

Le développement de l'application a nécessité la mise en place d'un environnement de travail structuré, reproductible et partagé par l'ensemble des contributeurs du projet. L'objectif était double~: garantir que chaque développeur travaille dans des conditions identiques, et disposer d'environnements distincts pour le développement, les tests et la production, afin d'éviter qu'une modification non maîtrisée n'impacte directement les utilisateurs finaux.

\subsection{Environnement de développement local}
Le projet repose sur la stack Angular (frontend) / NestJS (backend) / PostgreSQL (base de données), avec Prisma comme ORM. Pour homogénéiser les pratiques entre développeurs, les outils suivants ont été retenus et configurés à la racine du dépôt.

\paragraph{Éditeur de code et extensions.}
L'éditeur utilisé est Visual Studio Code, accompagné des extensions suivantes~:

    \centering

\paragraph{Gestion de la version de Node.js.}
Afin d'éviter les incompatibilités liées à des versions différentes de Node.js entre les postes de développement, la version utilisée est fixée à Node.js v20 (LTS) via un fichier \texttt{.nvmrc} placé à la racine du projet. Chaque développeur exécute la commande \texttt{nvm use} avant de lancer le projet, ce qui garantit que tous travaillent avec un environnement d'exécution identique.

\paragraph{Gestionnaire de paquets.}
La gestion des dépendances repose sur npm. Le fichier \texttt{package-lock.json} est versionné dans le dépôt Git, ce qui permet de figer précisément les versions des dépendances installées et d'éviter qu'une mise à jour involontaire d'un paquet ne provoque une régression chez un développeur et pas chez un autre.

\paragraph{Orchestration des services via Docker Compose.}
L'ensemble de l'environnement de développement local est orchestré par un unique fichier \texttt{docker-compose.yml}, qui décrit cinq services interdépendants. Cette approche garantit que tout nouveau développeur peut démarrer l'intégralité du projet avec une seule commande, sans installer Node.js, PostgreSQL ou un client S3 directement sur sa machine. L'option \texttt{develop.watch} de Docker Compose permet en outre de reconstruire automatiquement les images backend et frontend lorsque les fichiers de dépendances ou de variables d'environnement sont modifiés.

\subsection{Outils de qualité et de performance}
Plusieurs outils ont été intégrés à la chaîne de développement afin de garantir un niveau de qualité constant sur le code produit~:
\begin{itemize}
    \item \textbf{ESLint} : configuré avec les règles recommandées pour Angular et NestJS, exécuté automatiquement à chaque tentative de commit grâce à un hook \texttt{pre-commit} géré par Husky. Un commit contenant des erreurs de lint est bloqué avant d'atteindre le dépôt distant.
    \item \textbf{Prettier} : formatage automatique du code (indentation, guillemets, longueur de ligne), supprimant les débats de style et les diffs Git inutiles.
    \item \textbf{Jest} : tests unitaires côté backend (services, contrôleurs NestJS).
    \item \textbf{Jasmine / Karma} : outils natifs d'Angular, utilisés pour les tests unitaires côté frontend.
\end{itemize}

\subsection{Choix de l'infrastructure d'hébergement en production}
Le choix de la plateforme d'hébergement a été guidé par trois critères~: la cohérence avec la méthode de développement déjà en place (tout le projet est packagé en conteneurs via \texttt{docker-compose.yml}), la simplicité technique de mise en œuvre, et la sobriété environnementale de l'infrastructure cible.

\paragraph{Solution retenue : un VPS exploité avec le même docker-compose.yml.}
Plutôt que de migrer vers une architecture orchestrée (Kubernetes) ou vers des services managés distincts, le choix retenu est un serveur privé virtuel (VPS) unique sur lequel le \texttt{docker-compose.yml} de développement est réutilisé quasiment à l'identique~: seules les variables d'environnement et les options de montage de volumes liées au hot reload sont retirées pour la production. Les cinq services sont démarrés via \texttt{docker compose up -d}, exactement comme en local. Ce choix minimise la charge d'apprentissage et le risque d'erreur~: l'infrastructure de production est une transposition directe de l'environnement déjà maîtrisé en développement.

\paragraph{Critère écoresponsable.}
L'hébergeur retenu est Scaleway, fournisseur de cloud souverain français. Ce choix répond au critère de sobriété environnementale~: datacenters alimentés en énergie renouvelable (majoritairement hydraulique), indicateur d'efficacité énergétique (PUE) nettement sous la moyenne du secteur grâce au refroidissement adiabatique, implantation en France limitant la latence et s'appuyant sur un mix électrique parmi les moins carbonés d'Europe, et exécution native de Docker Compose. Une alternative équivalente, écartée pour ce projet mais documentée par souci de transparence, est Infomaniak (hébergeur suisse), au profil environnemental comparable mais hébergeant les données hors Union européenne.

\section{Intégration continue (C2.1.2)}
\competence{C2.1.2}{Protocole d'intégration continue}{Non}

Afin de détecter les régressions le plus tôt possible dans le cycle de développement, un pipeline d'intégration continue (CI) a été mis en place. Il s'exécute automatiquement à chaque modification du code source et empêche la fusion de code non conforme dans la branche principale.

\subsection{Choix de l'outil d'intégration continue}
L'outil retenu est GitLab CI/CD. Ce choix s'explique par son intégration native avec GitLab (le dépôt du projet y étant déjà hébergé), sa gratuité pour les projets publics et la simplicité de configuration des pipelines via un fichier YAML versionné directement dans le dépôt, ce qui rend la configuration du pipeline traçable au même titre que le code applicatif.

\subsection{Description du pipeline CI}
Le pipeline est défini dans le fichier \texttt{.gitlab-ci.yml}. Il se déclenche automatiquement à chaque push, quelle que soit la branche, ainsi qu'à chaque ouverture ou mise à jour d'une merge request vers la branche \texttt{main}.

\begin{table}[H]
    \centering
    \begin{tabular}{|c|>{\raggedright\arraybackslash}p{0.38\linewidth}|>{\raggedright\arraybackslash}p{0.38\linewidth}|}
        \hline
        \textbf{Étape} & \textbf{Action} & \textbf{Comportement en cas d'échec} \\
        \hline
        1 & Checkout du code source & --- \\
        \hline
        2 & Installation de Node.js (version fixée via .nvmrc) & --- \\
        \hline
        3 & Installation des dépendances (npm ci) & Le pipeline s'arrête si une dépendance ne peut être installée. \\
        \hline
        4 & Lint du code (npm run lint) & Bloque le pipeline si une erreur ESLint est détectée. \\
        \hline
        5 & Build de l'application (npm run build) & Bloque le pipeline si la compilation échoue. \\
        \hline
        6 & Exécution des tests unitaires (npm run test) & Bloque le pipeline si un test échoue. \\
        \hline
        7 & Génération et archivage du rapport de couverture & Le rapport est conservé en artefact, consultable depuis l'interface GitLab CI/CD. \\
        \hline
    \end{tabular}
    \caption{Séquences du pipeline d'intégration continue}
\end{table}

Chacune de ces étapes est bloquante~: si l'une d'elles échoue, les étapes suivantes ne sont pas exécutées et le pipeline est marqué en échec, ce qui empêche la fusion de la merge request concernée.

\subsection{Stratégie de gestion des branches}
La stratégie de branches adoptée vient renforcer l'efficacité du pipeline CI en structurant le flux de contribution au code.

\begin{table}[H]
    \centering
    \begin{tabular}{|>{\raggedright\arraybackslash}p{0.20\linewidth}|>{\raggedright\arraybackslash}p{0.68\linewidth}|}
        \hline
        \textbf{Branche} & \textbf{Rôle} \\
        \hline
        main & Branche de production, protégée. Aucun push direct~: toute modification passe par une merge request dont le pipeline CI doit être au vert avant fusion. \\
        \hline
        develop & Branche d'intégration sur laquelle les fonctionnalités sont fusionnées avant d'être intégrées à main. \\
        \hline
        feature/xxx & Branches de fonctionnalités, créées depuis develop pour chaque évolution, et supprimées une fois la fonctionnalité fusionnée. \\
        \hline
    \end{tabular}
    \caption{Stratégie de branches}
\end{table}

Cette organisation garantit qu'aucune régression ne peut être introduite en production sans avoir au préalable été détectée par le pipeline, et qu'une fonctionnalité en cours de développement n'impacte jamais directement la branche de production.
